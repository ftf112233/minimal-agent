# 架构设计题（第 4 题）：Agent 的幂等性与重试

> 题目原文：Agent 中有幂等性吗？幂等性对 Agent 框架有什么作用？Agent 中的幂等性
> 跟后端中台里面的幂等有什么区别？在 Agent 开发框架中，如何实现幂等性？
> 如果你的 Agent 开发框架需要对外提供 Agent 的重试能力，如何设计 Agent 的幂等性，
> 才能保证重试不会产生副作用？

---

## 0. 核心结论

Agent 中存在幂等性问题，而且比传统后端**更棘手**：因为 Agent 的"一次业务操作"
不再是"一次接口调用"，而是"N 次不可预测的 LLM 推理 + M 次工具调用"的组合。
重试的副作用边界从"一个接口"扩散到了"整条推理链"。
核心解法：**以"轮次"为幂等单元、以"确定性状态检查"代替"记忆式去重"、
以"工具幂等声明"代替"全局统一方案"。**

---

## 1. Agent 中有幂等性吗？

有，而且无处不在。先看我的 minimal-agent 里一个真实例子：

> 用户说"帮我记个待办：写周报" → LLM 决策调用 `todo(action=add, content=写周报)`。
> 如果这轮因为网络问题被重试，`add` 会再执行一次——**待办列表里出现两条"写周报"**。

这不是假设，是这套代码的真实行为：`todo_handler` 的 `add` 是典型的非幂等操作
（每次执行都改变状态，且无唯一性约束）。

幂等性问题在 Agent 里分布在三个层面：

| 层面 | 例子 | 重试后果 |
|------|------|---------|
| **工具层** | todo.add、下单、发消息、扣款 | 状态被重复变更（最常见） |
| **推理层** | LLM 生成的中间计划 | 重试后模型可能给出**不同的**工具调用序列 |
| **会话层** | history 追加、轮次计数 | 重复追加消息污染上下文 |

注意第二行是 Agent 特有的深坑：**LLM 是非确定性系统**（temperature>0、服务端
采样随机），同样输入重试一次，模型可能这次选了不同的工具、不同的参数。
这意味着传统后端"重试 = 重放同一个请求"的假设在 Agent 这里**不成立**。

## 2. 幂等性对 Agent 框架的作用

一句话：**幂等性是重试能力的前提，重试是可用性的前提**。

Agent 系统的调用链特别长（CLI/网关 → Runtime → LLM API → 工具 → 外部系统），
任何一环都可能瞬时失败。没有幂等性保障时，框架面临两难：

- 不敢重试 → 可用性差（LLM API 超时率不低，一次失败整轮报废）；
- 敢重试 → 可能重复下单/重复扣款/重复发消息 → **资损**。

所以幂等性决定了 Agent 框架能不能放心地提供这三样东西：
1. **工具级重试**（工具超时后自动再调一次）；
2. **轮次级重试**（整轮推理失败后用户点"重试"）；
3. **故障恢复**（进程崩溃后从检查点恢复继续跑）。

另外幂等性还有一个隐性收益：**重复请求去抖**。用户双击发送、客户端弱网自动重发、
上游消息队列 at-least-once 投递——这些"非刻意重试"同样需要幂等兜底。

## 3. Agent 的幂等 vs 后端中台的幂等：区别在哪

后端中台的成熟方案（以支付为例）：**幂等键 + 唯一索引/Redis SETNX**。
客户端为每笔交易生成唯一 `idempotency-key`，服务端见到重复 key 直接返回上次结果。
关键假设有两个：

1. **重放的是同一个请求**——参数完全一致；
2. **"执行过"可以被准确记录**——一个 key 一条记录。

Agent 场景下这两个假设都动摇了：

| 维度 | 后端中台 | Agent |
|------|---------|-------|
| 请求确定性 | 同 key 重放参数必然相同 | LLM 非确定性，重试可能产生**不同的工具调用序列** |
| 副作用边界 | 一个接口 | 一轮 N 步、每步可能带副作用，中途失败停在任意步 |
| "执行过"的定义 | 事务级，要么完整要么没有 | 推理链是**部分完成**的：可能工具 A 已执行、B 未执行 |
| 语义等价 | 字节级：参数相同即相同 | **语义级**：`add(content=写周报)` 和 `add(content=写周报!)` 字节不同但语义重复 |
| 判定时机 | 请求入口处，同步判定 | 副作用在工具内部发生，框架在入口处**看不见** |

所以后端幂等是"**入口去重**"问题，Agent 幂等是"**链路中任意点恢复 + 语义去重**"问题。
前者是数据库唯一索引能解决的，后者需要框架级的支持——这正是下一问。

## 4. Agent 开发框架如何实现幂等性

我认为要分三层来做，每层管自己的事：

### 4.1 工具层：幂等性声明（框架的基础设施）

幂等性只有工具作者自己知道——框架不可能知道 `add` 有副作用而 `list` 没有。
所以工具注册表应该**强制声明幂等属性**，就像声明参数 Schema 一样：

```python
@dataclass
class Tool:
    name: str
    description: str
    parameters: dict
    handler: ToolHandler
    idempotency: str = "none"   # none / natural / keyed
```

三档的含义：

- **natural（天然幂等）**：重复执行无副作用，如 `list`、`search`、`get_weather`。
  框架可以放心对它做任何重试。
- **keyed（可幂等化）**：本身不幂等，但支持幂等键，如 `order.create(order_id=X)`。
  框架自动为每次调用生成/透传幂等键，下游用唯一索引去重。
- **none（不可重试）**：既不天然幂等也不支持幂等键（比如对接的第三方接口
  就没提供幂等参数）。框架必须**禁止自动重试**，失败只能上抛或转人工。

这个分类决定了框架重试策略的下限：**重试的激进程度由工具的幂等声明约束**，
而不是由重试策略一厢情愿。

### 4.2 执行层：调用日志 + 确定性恢复

解决"推理链中途失败"的问题。框架记录每步执行结果（minimal-agent 里已有雏形：
`session.trace`），但要做两个增强：

1. **工具调用记录入库**：`(turn_id, step, tool_name, args_hash, result_hash, status)`；
2. **恢复时状态检查代替盲目重放**：整轮重试时，不是从头重跑，而是先查
   调用日志——前面哪些步已执行、结果是什么。已完成的步骤直接复用结果（重放
   Observation），只从失败点继续。

这就是"**以确定性状态检查代替记忆式去重**"：不依赖"我记住了这轮执行过"
（内存态不可靠），而是执行前查持久化的日志（崩溃后依然有效）。

### 4.3 语义层：LLM 造成的"隐性重复"兜底

最难的一层。即使框架层面完美幂等，LLM 也可能因为上下文丢失/压缩/换了个说法，
在两轮里生成语义重复的工具调用（第一轮 add 了"写周报"，第二轮用户追问时模型又 add 一次）。

务实的做法是**把语义去重的信息还给模型**：Observation 里带状态回显
（"已添加待办 #1: 写周报"——minimal-agent 已经这么做了，id 回显让模型下轮能引用），
并在 system prompt 中加入规则："执行写操作前，若上下文显示该操作已成功，不要重复执行"。
不完美，但成本极低，能挡住大部分语义重复。完全的语义去重（向量化比对）投入产出比太低，
我不建议在框架层做。

## 5. 框架对外提供"轮次级重试"能力时，如何保证无副作用

这是题目的最后一问，也是前面所有讨论的落点。场景：Agent 服务以 API 对外提供，
调用方失败后携带**同一个 turn_id** 重试整个轮次。设计如下：

### 5.1 幂等单元与键的设计

- **幂等单元 = turn（轮次）**，不是单次工具调用——因为调用方视角的"一次请求"
  就是完整一轮对话；
- **幂等键 = (session_id, turn_id, input_hash)**。`input_hash` 参与键的构成很关键：
  同一 turn_id 但输入变了（用户改了话再说），应当视为新请求而不是重试；
- 键的生成方：调用方（推荐，见 5.3 的讨论）。

### 5.2 完整流程

```
请求进来（session_id + turn_id + input + input_hash）
  │
  ▼ 第一步：轮次级去重（O(1)，Redis）
  ├─ SETNX idempotent:{session}:{turn}:{hash} TTL=24h
  ├─ 命中"处理中" ──► 返回 409/进行中状态（防并发双跑）
  ├─ 命中"已完成" ──► 直接返回缓存的结果（真重试，零副作用）
  └─ 未命中 ──► 标记"处理中"，开始推理
  │
  ▼ 第二步：链路执行（带调用日志）
  ├─ 每步工具调用前：查调用日志 (turn_id, step, args_hash)
  │    已存在且成功 ──► 直接复用结果作为 Observation（跳过实际执行）
  │    已存在且失败 ──► 对 natural/keyed 工具重试；none 工具上抛
  ├─ 每步执行后：追加调用日志（先落库再返回，保证崩溃后可恢复）
  │
  ▼ 第三步：完成
  ├─ 结果写入 idempotent 缓存，标记"已完成"
  └─ 返回结果
```

两个关键设计点：

**① 结果缓存的时效**：缓存"已完成"的结果时 TTL 要设置（如 24h）。太短起不到
幂等作用，太长会撞上"会话已演进"的问题——用户重试三天前的轮次，当时的答案现在
未必正确。超时后重试按新请求处理，靠 input_hash 和上下文自然区分。

**② 调用日志与业务事务的关系**：工具执行成功 → 日志落库成功，这两步之间崩溃了，
恢复时会出现"业务已执行但日志缺失"——此时会重复执行一次。这是 at-least-once 的
固有窗口，无法在框架层消灭（除非工具本身提供事务回查接口，如支付的单据查询）。
**诚实的结论：框架能把副作用概率从"每次重试都可能重复"降到"极端崩溃窗口内的
微小概率"，消灭最后一公里要靠工具侧的对账/回查能力。** 承认这个边界比假装
完美更可信。

### 5.3 与后端中台幂等的键生成差异

后端幂等键通常由**客户端**生成（支付场景：客户端为每笔交易生成 key）。
Agent 场景我建议：**turn_id 由调用方生成，input_hash 由 Agent 服务计算**。
原因：调用方最清楚"这是不是同一次业务意图"（用户的重试 vs 新输入），
而 hash 的算法是服务端实现细节，不该暴露给调用方。

## 6. 落到我的 minimal-agent 上（结合 vibe coding 答案）

这套设计在我的最小实现里对应到哪些位置，以及为什么当前实现可以不做：

| 设计要素 | minimal-agent 现状 | 为什么最小实现可以不做 |
|----------|-------------------|----------------------|
| 工具幂等声明 | 无，`Tool` 没有该字段 | CLI 单用户场景，无自动重试整轮的需求 |
| 工具级重试 | LLM 调用有（指数退避），**工具没有**——刻意为之 | 工具重试必须先有幂等声明，否则 todo.add 重试就会重复插入。**没有幂等保障就不提供工具重试，这本身就是幂等设计** |
| 轮次级去重 | 无 | 无外部调用方，重试入口就是用户手动重输 |
| 调用日志 | `session.trace` 是雏形（有 step、action、结果），但只追加不查询 | 恢复逻辑未实现，日志仅用于观察 |
| 状态回显防语义重复 | 已做：Observation 回带 `#1` 这样的 id | 成本为零的语义幂等辅助 |

如果要演进：`Tool` 加 `idempotency` 字段 → `registry.execute` 按 declares 决定是否
允许重试 → `handle()` 入口加 `(session_id, turn_id)` 去重 → trace 升级为可查询的
调用日志。每一步都是纯增量，不动主循环——这也验证了原架构的扩展性。

## 7. 取舍与边界

- **为什么不把幂等做进 LLM 调用层？** LLM 调用本身天然近似幂等（同输入同输出分布，
  无副作用），不值得做；真正的副作用都在工具层。
- **为什么不搞分布式事务（Saga/TCC）？** 重试场景幂等键方案复杂度低一个数量级；
  Saga 是补偿型方案，适合跨服务长事务，不是"重复请求"问题的对症药。
- **语义幂等为什么不上向量检索？** 误杀率高（"查北京天气"和"查上海天气"向量很近）、
  延迟高、依赖重。用"状态回显 + prompt 约束"覆盖 80% 场景，剩下 20% 接受。
- **并发下的双跑**：SETNX 标记"处理中"防的是同一轮次的并发重试；不同轮次并发
  本来就允许（session 级有锁或乐观并发控制，那是另一个话题）。

---

### 一句话总结

> Agent 的幂等性难点在于：副作用散布在不可预测的多步推理链上，且 LLM 的非确定性
> 打破了"重试=重放"的传统假设。框架的解法是三层各司其职——工具层**声明**幂等性、
> 执行层用**调用日志做确定性恢复**、语义层用**状态回显**兜底；对外提供轮次级重试时，
> 以 (session, turn, input_hash) 为幂等键，入口去重 + 步级结果复用，
> 并诚实接受 at-least-once 残余窗口——最后一公里由工具侧对账能力收口。
